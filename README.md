# Distributed Caching System

Распределённая система кэширования на Rust, совместимая с Redis-клиентами (RESP2).

## Статус проекта

В разработке. Реализованы этапы:

- **Этап 1** — Базовый асинхронный TCP-сервер (PING/PONG) ✅
- **Этап 2** — Парсинг RESP2 (nom-парсер, потоковый буфер) ✅
- **Этап 3** — In-memory хранилище и основные команды (SET, GET, DEL, EXISTS, ECHO, PING, TTL) ✅
- **Этап 4** — Ограничение памяти и вытеснение (LRU) ✅
- **Этап 5** — Персистентность (RDB / AOF) ✅
- **Этап 6** — Контейнеризация и CI/CD ✅
- **Этап 7** — Кластеризация (consistent hashing, проксирование) ✅

## Стек

- Rust (edition 2024)
- Tokio (асинхронный I/O)
- DashMap 6 (конкурентное in-memory хранилище)

## Быстрый старт

```bash
cd distributed-cache-rust
cargo run
```

Сервер запускается на `127.0.0.1:8080`.

Проверка через redis-cli:

```bash
redis-cli -p 8080 PING
# Ожидаемый ответ: PONG
```

## Поддерживаемые команды

| Команда | Описание | Пример |
|---------|----------|--------|
| `PING` | Проверка доступности | `PING` → `PONG` |
| `PING msg` | Эхо-сообщение | `PING hello` → `"hello"` |
| `ECHO msg` | Возвращает сообщение | `ECHO hello` → `"hello"` |
| `SET key value [EX seconds]` | Установить ключ с опциональным TTL | `SET k v EX 10` → `OK` |
| `GET key` | Получить значение | `GET k` → `"v"` |
| `DEL key [key ...]` | Удалить один или несколько ключей | `DEL k1 k2` → `2` |
| `EXISTS key [key ...]` | Проверить существование | `EXISTS k` → `1` |
| `BGSAVE` | Сохранить RDB-снимок | `BGSAVE` → `OK` |

## Ограничение памяти и LRU-вытеснение (Этап 4)

Хранилище использует приближённый LRU-алгоритм (sample-based LRU) для ограничения потребления памяти:

- **Конфигурация:** `StoreConfig.max_memory_mb` — максимальный объём памяти в мегабайтах (по умолчанию 128 МБ).
- **Учёт памяти:** для каждой записи учитывается длина ключа + длина значения + 128 байт накладных расходов. Счётчик `used_memory` хранится в `AtomicU64`.
- **Вытеснение:** при добавлении нового ключа, если `used_memory > max_memory`, выбирается случайная выборка из 5 ключей. Среди них находится ключ с самой старой меткой `last_access` и удаляется. Процесс повторяется до снижения памяти ниже лимита.
- **Метка доступа:** `last_access` обновляется при каждом `GET` и `SET`.
- **Фоновая очистка TTL:** раз в 100 мс обходится случайная выборка из 20 ключей, истёкшие удаляются.

## Персистентность: RDB и AOF (Этап 5)

Данные сохраняются на диск двумя механизмами:

### RDB (снимки состояния)

- Периодически (каждые 60 секунд) или по команде `BGSAVE` создаётся полный снимок всех неистёкших записей.
- Формат: последовательность RESP2-команд `SET key value` (с опциональным `EX <ttl>`).
- Запись ведётся во временный файл (`dump.rdb.tmp`), затем атомарно переименовывается в `dump.rdb`.
- При старте сервер загружает RDB-снимок, если AOF выключен.

### AOF (журнал команд)

- Каждая изменяющая команда (`SET`, `DEL`) дописывается в файл `appendonly.aof` в формате RESP2.
- Файл открывается лениво при первой записи.
- Сброс на диск — каждые 2 секунды.
- При старте AOF имеет приоритет над RDB (восстанавливает состояние точнее).

### Конфигурация

Параметры задаются через `PersistenceConfig`:
- `data_dir` — директория для файлов (по умолч. `./data`)
- `rdb_filename` / `aof_filename` — имена файлов
- `snapshot_interval_secs` — интервал фоновых снимков (0 = отключено)
- `aof_enabled` — включение AOF

## Контейнеризация (Этап 6)

### Docker

Сборка образа и запуск одного узла:

```bash
cd distributed-cache-rust
docker build -t distributed-cache-rust .
docker run -d --name cache-node \
  -e CACHE_BIND=0.0.0.0:8080 \
  -p 8080:8080 \
  distributed-cache-rust
```

Проверка через netcat:

```bash
printf '*1\r\n$4\r\nPING\r\n' | nc -w 3 localhost 8080
# Ожидаемый ответ: +PONG
```

### Docker Compose (кластер из 2 узлов)

```bash
docker compose up -d
```

Поднимаются три контейнера:

| Контейнер | Назначение | Порт (хост) |
|-----------|------------|-------------|
| `cache-node-1` | Узел кэша №1 | `8080` |
| `cache-node-2` | Узел кэша №2 | `8081` |
| `cache-client` | Клиентский контейнер с `nc` | — |

После запуска можно выполнять запросы из `cache-client`:

```bash
# Подключиться к клиентскому контейнеру
docker exec -it cache-client bash

# Внутри контейнера:
printf '*3\r\n$3\r\nSET\r\n$1\r\na\r\n$1\r\n1\r\n' | nc -w 3 cache-node-1 8080
printf '*2\r\n$3\r\nGET\r\n$1\r\na\r\n' | nc -w 3 cache-node-2 8080
```

Остановка кластера:

```bash
docker compose down -v   # -v удаляет volumes с данными
```

### Переменные окружения

| Переменная | По умолчанию | Описание |
|------------|-------------|----------|
| `CACHE_BIND` | `127.0.0.1:8080` | Адрес и порт для привязки сервера |
| `CACHE_CLUSTER` | не задана | JSON-список узлов кластера (включает кластеризацию) |

## Кластеризация (Этап 7)

Система поддерживает распределение ключей между несколькими узлами
через **consistent hashing** (SHA-256, 256 виртуальных узлов на сервер).

### Настройка

```bash
# Запуск двух узлов:

# Терминал 1: узел A (порт 8080)
CACHE_CLUSTER='[{"address":"127.0.0.1:8080","vnodes":256},{"address":"127.0.0.1:8081","vnodes":256}]' \
  cargo run

# Терминал 2: узел B (порт 8081)
CACHE_BIND=127.0.0.1:8081 \
  CACHE_CLUSTER='[{"address":"127.0.0.1:8080","vnodes":256},{"address":"127.0.0.1:8081","vnodes":256}]' \
  cargo run
```

### Поведение

- Ключ хешируется → определяется владелец на кольце.
- Если ключ принадлежит другому узлу — сервер **проксирует** запрос:
  открывает TCP-соединение к целевому узлу, пересылает команду
  и возвращает ответ клиенту.
- Проксирование прозрачно: клиент не видит разницы.
- Для multi-key команд (DEL, EXISTS) маршрутизация по первому ключу.
