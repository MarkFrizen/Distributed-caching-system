# Кластеризация: Consistent Hashing

Система поддерживает распределение ключей между несколькими узлами
с помощью **consistent hashing**. Кластеризация включается через
переменную окружения `CACHE_CLUSTER`; если она не задана — сервер
работает в single-node режиме.

---

## Consistent Hashing

### Алгоритм

- **Хеш-функция:** SHA-256 (используются младшие 64 бита).
- **Кольцо:** виртуальные узлы (`vnodes`) каждого реального сервера
  размещаются на кольце диапазона `[0, 2^64)`.
- **Виртуальные узлы:** каждый реальный узел представлен `num_vnodes`
  (по умолчанию 256) точками на кольце. Хеш виртуального узла:
  `SHA-256("address:index")` (младшие 64 бита).
- **Поиск:** хеш ключа → ближайший виртуальный узел на кольце
  (с wrap-around) → адрес реального сервера.
- **Свойства:** при добавлении/удалении узла перемещается только
  доля ключей, пропорциональная доле его виртуальных узлов
  (в среднем `1/N`).

### Ключевые преимущества

1. **Минимальное перемещение** — при смене состава кластера
   перераспределяется только часть ключей, а не все.
2. **Детерминированность** — одинаковое хеш-кольцо на всех узлах
   гарантирует консистентное отображение ключей.
3. **Равномерное распределение** — 256 виртуальных узлов на сервер
   обеспечивают разброс не хуже ±10% относительно равномерного.

## Конфигурация

### Переменная окружения `CACHE_CLUSTER`

JSON-список узлов кластера:

```json
[
  {"address":"127.0.0.1:8080","vnodes":256},
  {"address":"127.0.0.1:8081","vnodes":256}
]
```

- `address` — адрес узла в формате `ip:port`.
- `vnodes` — количество виртуальных узлов (рекомендуется 256).

### Пример для Docker Compose

```yaml
services:
  cache-node-1:
    image: distributed-cache
    environment:
      CACHE_BIND: "0.0.0.0:8080"
      CACHE_CLUSTER: '[{"address":"cache-node-1:8080","vnodes":256},{"address":"cache-node-2:8081","vnodes":256}]'
```

## Маршрутизация запросов

### Локальная обработка

Если ключ принадлежит текущему узлу — команда выполняется
непосредственно (Store + AOF-логирование).

### Проксирование (Proxy)

Если ключ принадлежит другому узлу — сервер автоматически
открывает TCP-соединение к целевому узлу, пересылает RESP2-запрос
и возвращает ответ клиенту. Проксирование **прозрачно** для клиента:
он получает тот же ответ, как если бы обратился напрямую.

### Таймауты

- Подключение к целевому узлу: **5 секунд**
- Запись запроса: **5 секунд**
- Чтение ответа: **5 секунд**

При ошибке проксирования клиенту возвращается RESP-ошибка
с описанием причины.

### Multi-key команды (DEL, EXISTS)

Маршрутизация выполняется по **первому ключу**. Все остальные ключи
должны принадлежать тому же узлу (аналогично Redis Cluster).
При несовпадении поведение не определено — рекомендуется использовать
только ключи, попадающие на один узел, в рамках одной команды.

## Безопасность

- **Хеш-функция:** SHA-256 — криптостойкая, коллизии практически
  исключены. Использование в consistent hashing не требует
  криптографической стойкости, но даёт равномерное распределение.
- **Ошибки сети:** все операции с удалёнными узлами обёрнуты в
  `tokio::time::timeout`; сетевая ошибка не влияет на локальное
  хранилище.
- **Отсутствие `unwrap()`:** в production-коде маршрутизации нет
  вызовов `unwrap()`/`expect()`. Ошибки логируются через `tracing::warn!`
  и возвращаются клиенту как RESP-ошибки.

## Конфигурация по умолчанию

| Параметр | Значение по умолчанию | Описание |
|----------|-----------------------|----------|
| `CACHE_CLUSTER` | не задана | Single-node режим |
| `default_vnodes` | 256 | Виртуальных узлов на сервер |

## Пример: запуск двухузлового кластера

```bash
# Терминал 1: узел A
$ export CACHE_CLUSTER='[{"address":"127.0.0.1:8080","vnodes":256},{"address":"127.0.0.1:8081","vnodes":256}]'
$ cargo run

# Терминал 2: узел B
$ export CACHE_BIND=127.0.0.1:8081
$ export CACHE_CLUSTER='[{"address":"127.0.0.1:8080","vnodes":256},{"address":"127.0.0.1:8081","vnodes":256}]'
$ cargo run

# Терминал 3: клиент
$ redis-cli -p 8080 SET mykey value
OK
$ redis-cli -p 8081 GET mykey
"value"
```
