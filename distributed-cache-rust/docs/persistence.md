# Персистентность: RDB и AOF

Система поддерживает два механизма сохранения данных на диск:
**RDB** (снапшоты состояния) и **AOF** (журнал изменяющих команд).

---

## RDB (Redis Database) — снапшоты

### Формат файла

RDB-файл представляет собой последовательность RESP2-фреймов — по одному на каждую запись.

**Без TTL:**
```
*3\r\n$3\r\nSET\r\n$<key_len>\r\n<key>\r\n$<val_len>\r\n<value>\r\n
```

Пример для `SET mykey myvalue`:
```
*3\r\n$3\r\nSET\r\n$5\r\nmykey\r\n$7\r\nmyvalue\r\n
```

**С TTL:**
```
*5\r\n$3\r\nSET\r\n$<key_len>\r\n<key>\r\n$<val_len>\r\n<value>\r\n$2\r\nEX\r\n$<ttl_secs>\r\n<ttl>\r\n
```

Пример для `SET temp x EX 60`:
```
*5\r\n$3\r\nSET\r\n$4\r\ntemp\r\n$1\r\nx\r\n$2\r\nEX\r\n$2\r\n60\r\n
```

### Алгоритм сохранения

1. `Store::snapshot_entries()` собирает все неистёкшие записи с оставшимся TTL.
2. Каждая запись сериализуется в RESP2-массив `[SET, key, value]` или `[SET, key, value, EX, ttl]`.
3. Все фреймы конкатенируются в один буфер.
4. Буфер записывается во временный файл (`<filename>.rdb.tmp`).
5. Файл атомарно переименовывается в целевой (`<filename>.rdb`).

### Алгоритм загрузки

1. Файл читается целиком в память.
2. `RespBuffer` последовательно разбирает RESP2-фреймы.
3. Каждый фрейм-массив преобразуется в `Command::Set` и выполняется на хранилище.

### Тrigгеры сохранения

- **BGSAVE** — команда от клиента, синхронная (в текущей асинхронной задаче).
- **По таймеру** — каждые `snapshot_interval_secs` секунд (по умолчанию 60).
- Отключение: `snapshot_interval_secs: 0`.

## AOF (Append-Only File) — журнал команд

### Формат файла

AOF-файл содержит те же RESP2-фреймы, что были получены от клиента, но только для
**изменяющих** команд (`SET`, `DEL`). Команды `PING`, `GET`, `EXISTS`, `ECHO` не логируются.

Пример содержимого AOF после `SET a 1` и `DEL a`:
```
*3\r\n$3\r\nSET\r\n$1\r\na\r\n$1\r\n1\r\n
*2\r\n$3\r\nDEL\r\n$1\r\na\r\n
```

### Алгоритм записи

1. После выполнения изменяющей команды (`cmd.is_modifying() == true`)
   вызывается `persistence.append_command(frame)`.
2. Файл открывается **лениво** — при первой записи (режим append).
3. Данные дописываются в конец файла асинхронно через `file.write_all()`.
4. Периодический сброс на диск (`flush`) — каждые 2 секунды.

### Алгоритм загрузки (replay)

1. Файл читается целиком.
2. `RespBuffer` разбирает RESP2-фреймы.
3. Каждый фрейм преобразуется в `Command` и выполняется на хранилище.

### Приоритет загрузки

При старте сервера:
- Если **AOF включён** → загружается только AOF (он точнее отражает состояние).
- Иначе → загружается RDB-снимок (если существует).

## Конфигурация

Параметры задаются через структуру `PersistenceConfig`:

| Поле | Тип | По умолчанию | Описание |
|------|-----|-------------|----------|
| `data_dir` | `PathBuf` | `./data` | Директория для RDB и AOF-файлов |
| `rdb_filename` | `String` | `dump.rdb` | Имя RDB-файла |
| `aof_filename` | `String` | `appendonly.aof` | Имя AOF-файла |
| `snapshot_interval_secs` | `u64` | `60` | Интервал фоновых снимков (0 = отключено) |
| `aof_enabled` | `bool` | `true` | Включить AOF-журнал |

Пример кастомной конфигурации:

```rust
let config = PersistenceConfig {
    data_dir: "/var/lib/cache".into(),
    rdb_filename: "snapshot.rdb".into(),
    aof_enabled: true,
    snapshot_interval_secs: 300, // каждые 5 минут
    ..Default::default()
};
```

## Безопасность

- **Атомарная запись RDB:** запись во временный файл → `rename()`. Даже при
  сбое во время записи предыдущий корректный снимок не повреждается.
- **Обработка ошибок:** все ошибки ввода-вывода логируются через `tracing::error!()`
  и возвращают RESP-ошибку клиенту (`-ERR ...`). Никаких `unwrap()`/`panic!` в production-коде.
- **Загрузка повреждённых файлов:** при ошибке чтения/разбора логируется
  предупреждение (`warn!`), сервер продолжает работу с пустым хранилищем.
