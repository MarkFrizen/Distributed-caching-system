# Нагрузочное тестирование

## Инструменты

1. **Собственный Rust-клиент** (`src/bin/benchmark.rs`) — измеряет QPS, P50/P99/P99.9 латентность
   для SET/GET/MIXED с разным числом параллельных соединений.
2. **Микробенчмарки** (`--microbench`) — in-process замеры операций парсинга, кодирования RESP2
   и базовых операций HashMap.
3. **redis-benchmark** (через `redis:alpine`) — для сравнения с эталонными метриками Redis.

## Условия тестирования

- **Среда:** Docker-контейнер на Windows (Debian bookworm-slim), release-сборка
- **Железо:** см. примечание — результаты на Windows через Docker Desktop имеют
  накладные расходы виртуализации
- **Размер значения:** 256 байт
- **Конфигурация сервера:** single-node, без кластеризации, без репликации, AOF включён

## Анализ

### Пропускная способность
- **~28 000 QPS** при MIXED нагрузке (50-200 соединений)
- **~15 000 QPS** для SET, **~26 000 QPS** для GET
- QPS практически не падает при росте с 50 до 200 соединений (28K → 27.5K) —
  сервер масштабируется в пределах протестированного диапазона

### Латентность

- **P50:** 0.7-5.2 ms (зависит от числа соединений)
- **P99:** 1.1-15.2 ms
- **P99.9:** 2.4-17.5 ms
- GET быстрее SET (~1.8 ms vs ~3.3 ms P50) — ожидаемо, так как SET требует
  записи в AOF

### Масштабирование

При увеличении соединений с 1 до 50 пропускная способность растёт в 21 раз
(1,330 → 28,114 QPS), что демонстрирует эффективность tokio async I/O.

### Потребление памяти

По умолчанию сервер работает с лимитом 128 MB, LRU-вытеснение удерживает
память в заданных пределах.

---

## Выводы

- Rust + Tokio обеспечивают предсказуемую производительность с низкой вариативностью
  задержек (P99.9 близок к P99)
- Парсинг RESP2 не является узким местом (< 10 нс)
- Влияние AOF на производительность SET минимально (~2 ms разницы с GET)
- Сервер стабильно держит ~28 000 QPS без единой ошибки
