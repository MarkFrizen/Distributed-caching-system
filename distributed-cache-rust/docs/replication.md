# Репликация (master‑slave)

## Общая схема

Репликация реализована по упрощённой модели **один мастер — много реплик**:

1. **Master** принимает запросы на запись (SET, DEL) и транслирует их всем
   подключённым репликам.
2. **Replica** подключается к мастеру, отправляет команду `SYNC`, получает
   полный снимок данных и затем поток живых изменяющих команд.

При разрыве соединения реплика автоматически переподключается через 1 секунду.

## Протокол SYNC

1. Реплика открывает TCP-соединение к мастеру и отправляет:
   ```
   *1\r\n$4\r\nSYNC\r\n
   ```
2. Мастер отвечает:
   - Последовательностью RESP2-команд `SET` для каждого живого ключа.
   - Маркером `+SYNC_DONE\r\n`, означающим конец снимка.
3. После маркера мастер начинает транслировать каждую изменяющую команду
   (SET, DEL) в реальном времени как один RESP2-фрейм.

Реплика читает все входящие RESP2-фреймы и применяет их к локальному
хранилищу. Маркер `+SYNC_DONE` используется для логирования; реплика
начинает применять команды сразу (и снимок, и поток — однородная
последовательность SET/DEL-фреймов).

## Конфигурация (переменные окружения)

| Переменная | Описание | По умолчанию |
|---|---|---|
| `CACHE_ROLE` | Роль узла: `"master"` или `"replica"` | (репликация отключена) |
| `CACHE_MASTER` | Адрес мастера (только для реплики) | `127.0.0.1:8080` |

### Пример запуска мастера

```bash
set CACHE_ROLE=master
cargo run
```

### Пример запуска реплики

```bash
set CACHE_ROLE=replica
set CACHE_MASTER=127.0.0.1:8080
cargo run
```

## Архитектура (код)

### `replication/mod.rs`

- **`ReplicationConfig`** — парсит `CACHE_ROLE`/`CACHE_MASTER` из окружения.
- **`ReplicationRole`** — enum: `Master` | `Replica { master_addr }`.
- **`MasterState`** — хранит `broadcast::Sender<Vec<u8>>`. Метод `handle_sync()`
  отправляет снимок и транслирует живые команды.
- **`spawn_replica_client()`** — фоновая задача: подключается к мастеру,
  отправляет SYNC, читает и применяет команды. При разрыве — переподключение.

### `main.rs`

- При `CACHE_ROLE=master` создаётся `MasterState::new()` и передаётся
  в `handle_connection`.
- После выполнения каждой изменяющей команды `cmd.is_modifying()` фрейм
  отправляется в `master_state.sender()`.
- При получении команды `SYNC` управление соединением передаётся
  в `master_state.handle_sync()`, который захватывает поток.

## Тестирование

Два интеграционных теста в `replication/tests`:

1. **`integration_master_replica_sync`**:
   - Запускает master и replica.
   - SET на мастере → GET на реплике.
   - DEL на мастере → GET на реплике возвращает nil.

2. **`integration_replica_gets_snapshot`**:
   - Мастер с предзаполненными данными.
   - Реплика подключается и получает весь снимок.

## Ограничения (упрощения)

- Нет частичного пересинхрона (PSYNC) — при каждом переподключении реплика
  получает полный снимок.
- Мастер не буферизирует команды «на потом» — если реплика отключена,
  команды теряются (восстанавливаются при следующем полном SYNC).
- Реплика хранит данные только в памяти (без персистентности).
- Нет репликации AOF на реплике — при перезапуске реплика синхронизируется
  заново.
